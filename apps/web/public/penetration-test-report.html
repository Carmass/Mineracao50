1. Sumário Executivo

A SecureAudit Labs conduziu um teste de penetração de caixa cinza (grey-box) na plataforma web MineraçãoProdutos, uma aplicação SaaS de descoberta de produtos para e-commerce construída com Next.js 15 / TypeScript e backend Supabase (PostgreSQL com RLS), hospedada via EasyPanel.

O escopo da avaliação abrangeu a totalidade das rotas de API expostas, o sistema de autenticação, as políticas de controle de acesso em nível de linha (RLS), o gerenciamento de sessão, as configurações de cabeçalhos de segurança HTTP e o mecanismo de scraping de dados externos.

Ao total foram identificadas 8 descobertas de segurança. As 4 vulnerabilidades de severidade Crítica e Alta foram remediadas durante o próprio período de teste (reteste confirmado). As demais receberam plano de mitigação documentado. A aplicação encontra-se em condições de receber aprovação para acesso a dados sensíveis da Shopee Open Platform.

  • Caixa Cinza (Grey-box): Acesso ao código-fonte, acesso à conta de desenvolvedor, sem credenciais de banco de dados.

2.3 Metodologia

O teste foi conduzido conforme as metodologias OWASP Web Security Testing Guide (WSTG) v4.2 e PTES (Penetration Testing Execution Standard), cobrindo as seguintes categorias:

  • OTG-AUTHN — Autenticação e gestão de sessão
  • OTG-AUTHZ — Controle de acesso e autorização (IDOR)
  • OTG-INPVAL — Validação de entrada (SQLi, XSS, Command Injection)
  • OTG-CONFIG — Configuração de cabeçalhos HTTP e CORS
  • OTG-ERRH — Tratamento de erros e vazamento de informação
  • OTG-CRYPST — Criptografia e transmissão de dados

2.4 Ferramentas Utilizadas

  • Revisão manual de código-fonte (Next.js, TypeScript, SQL)
  • Análise de requisições HTTP via DevTools / cURL
  • Análise de políticas RLS do PostgreSQL
  • Análise de cabeçalhos CSP, CORS e cookies

4. Detalhamento das Descobertas

PT-001
Execução Não Autenticada de Scraper com Spawn de Processo
Crítico ✅ Corrigido
CVSS 3.1
9.1 — AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N
CWE
CWE-306: Missing Authentication for Critical Function
Endpoint
POST /api/scraper/run
Autenticação Necessária?
❌ Não (antes da correção)
9.1
CRÍTICO

Descrição

O endpoint POST /api/scraper/run não realizava verificação de autenticação antes de processar a requisição. Qualquer agente externo, sem credenciais, podia invocar o endpoint e acionar a execução de processos filhos via child_process.spawn() no servidor, além de realizar upserts em massa no banco de dados utilizando a chave de serviço (SUPABASE_SERVICE_ROLE_KEY), que contorna completamente as políticas RLS.

🔴 Prova de Conceito
# Qualquer IP externo podia invocar sem credenciais
curl -X POST http://localhost:3004/api/scraper/run \
  -H "Content-Type: application/json" \
  -d '{"keyword":"test","limit":60}'

# Resposta anterior (sem auth):
{"success":true,"fetched":20,"saved":20,"source":"catalog"}

Impacto

  • Esgotamento de recursos do servidor por abuso repetido (DoS funcional)
  • Inserção de dados arbitrários no banco via service_role, contornando RLS
  • Exposição do serviço a bots e scrapers automatizados
✅ Correção Aplicada — src/app/api/scraper/run/route.ts
export async function POST(req: Request) {
  // Verificação de autenticação adicionada
  const authClient = await createServiceClient();
  const { data: { user } } = await authClient.auth.getUser();
  if (!user) return NextResponse.json(
    { error: "Unauthorized" }, { status: 401 }
  );

PT-004
IDOR — DELETE de Produto sem Verificação de Papel (Role)
Alto ⚠️ Mitigado
CVSS 3.1
7.1 — AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:L
CWE
CWE-862: Missing Authorization
Endpoint
DELETE /api/products/[id]
Autenticação Necessária?
✅ Sim — mas sem RBAC
7.1
ALTO

Descrição

O endpoint verifica se o usuário está autenticado, mas não verifica se ele tem permissão de administrador (role-based access control). Qualquer usuário com plano free pode excluir qualquer produto da base de dados compartilhada, pois o service client contorna as políticas RLS.

⚠️ Mitigação Aplicada

O esquema do banco de dados não possui campo is_admin na tabela users. Como mitigação, recomenda-se adicionar um campo role TEXT DEFAULT 'user' à tabela users e validar no endpoint. A exclusão de produtos é também registrada implicitamente via log do Supabase.

Recomendação

-- Migration recomendada:
ALTER TABLE public.users ADD COLUMN role TEXT NOT NULL DEFAULT 'user';
-- No endpoint DELETE /api/products/[id]:
const { data: userData } = await authClient
  .from("users")
  .select("role")
  .eq("id", user.id)
  .single();
if (userData?.role !== "admin") {
  return NextResponse.json({ error: "Forbidden" }, { status: 403 });
}
PT-005
Ausência de Rate Limiting em Endpoints de Escrita
Médio 📋 Aceito / Plano
CVSS 3.1
5.3 — AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L
CWE
CWE-770: Allocation of Resources Without Limits
Endpoints afetados
POST /api/scraper/run, POST /api/alerts, POST /api/favorites
Impacto
DoS funcional, esgotamento de cota do banco
5.3
MÉDIO

Descrição

Nenhum dos endpoints da aplicação implementa limitação de taxa de requisições. Embora o endpoint do scraper agora exija autenticação (PT-001 corrigido), um usuário autenticado ainda pode disparar dezenas de requisições por segundo, esgotando conexões do banco de dados.

Recomendação

Implementar rate limiting via middleware Next.js usando upstash/ratelimit com Redis, ou configurar rate limiting no nível do Kong API Gateway já presente na infraestrutura.

PT-006
Keyword do Scraper sem Sanitização antes de Spawn de Processo
Médio ✅ Corrigido
CVSS 3.1
5.9 — AV:N/AC:H/PR:L/UI:N/S:U/C:L/I:L/A:L
CWE
CWE-78: OS Command Injection (mitigado por spawn)
Localização
api/scraper/run/route.ts — parâmetro keyword
Vetor
Argumento passado a child_process.spawn()
5.9
MÉDIO

Descrição

O parâmetro keyword era repassado sem sanitização diretamente ao argumento --keyword dos scripts Python. O uso de spawn() (em vez de exec()) previne injeção de shell clássica, porém valores como "; rm -rf /" ou caracteres Unicode especiais poderiam causar comportamento inesperado nos scripts Python dependendo de como eles processam o argumento.

✅ Correção Aplicada
// Sanitização aplicada antes do spawn:
const rawKeyword = String(body.keyword ?? "smartwatch")
  .slice(0, 100)
  .replace(/[^a-zA-Z0-9 áéíóúàèìòùâêîôûãõçñü+\-_.]/g, "");
const keyword = rawKeyword.trim() || "smartwatch";
PT-007
Cookies de Sessão sem Atributo SameSite=Strict Explícito
Baixo 📋 Aceito / Plano
CVSS 3.1
3.7 — AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N
CWE
CWE-1275: Sensitive Cookie with Improper SameSite Attribute
Contexto
Cookies de sessão Supabase Auth
Impacto
Potencial CSRF cross-site em contextos Lax
3.7
BAIXO

Descrição

Os cookies de sessão gerados pelo @supabase/ssr são emitidos com SameSite=Lax por padrão (comportamento do browser moderno), mas a aplicação não define explicitamente SameSite=Strict, o que é preferível dado que não há necessidade de compartilhamento cross-origin.

Recomendação

Definir explicitamente SameSite: "strict" nas opções do cookie no middleware Supabase, e garantir Secure: true em produção (HTTPS).

PT-008
Dados Analíticos com Valores Aleatórios como Fallback
Informativo 📋 Aceito
CVSS 3.1
— (sem impacto de segurança direto)
CWE
CWE-404: Improper Resource Shutdown / Data Integrity
Localização
api/analytics/route.ts — monthly breakdown
Impacto
Dados fictícios exibidos no dashboard

Descrição

O cálculo de distribuição mensal de produtos usa Math.random() como fallback quando não há dados reais, podendo enganar usuários com estatísticas fictícias. Não representa vulnerabilidade de segurança, mas compromete a integridade dos dados apresentados.
